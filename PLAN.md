# PLAN.md: grant-ps.com personal blog

Implementation brief for the agent building this repo. Read it fully before starting. Every decision in "Settled decisions" was made deliberately with its trade-offs in view: implement them, do not relitigate them. If something in this plan turns out to be impossible or clearly wrong, stop and say so rather than quietly working around it.

## 1. Context and goal

Grant (GitHub `grantspeelman`) is moving his writing off third-party platforms onto his own domain, **grant-ps.com**. This build is a **time-boxed experiment**: can a personal blog with an AI-driven publishing workflow be stood up in a few hours? The story of the build becomes the blog's first post, so you are building the platform *and* producing the raw material for that post (see the build log, section 9).

Target: roughly **3 hours of agent work** for everything in this plan. If you are clearly going to overrun, say so in the build log and to Grant, and propose what to cut, rather than silently expanding.

The core idea:

- **Markdown is the source of truth for content.** Each post is a markdown file with frontmatter.
- **Claude writes each post's HTML directly** from the markdown, using a design brief and a shared page shell. This is deliberate: it allows creative flare per post, and the whole site can be reinvented later by regenerating from the markdown.
- **Boring, deterministic code does everything that must be exact**: the RSS feed, the sitemap, and a fidelity guard that proves the generated page contains the author's exact words.
- **The deploy is dumb.** Everything that goes live is generated and reviewed locally, committed, and pushed. Cloudflare only serves committed files. No build step, no scripts, no API keys in the deploy.

## 5. Content model

### Frontmatter

```yaml
---
title: "Building my own blog in an afternoon"
slug: building-my-own-blog        # must equal the folder name; frozen once published
date: 2026-10-05                  # publication date (ISO 8601)
updated: 2026-10-06               # optional
description: "One or two sentences. Used for meta description, social cards, feed summary."
tags: [ai, ruby, blogging]        # max 4; lowercase a-z0-9 only; max 20 chars each (dev.to rules)
og_image: cover.png               # optional; relative to the post folder; falls back to site default
---
```

Validation (in `lib/`, used by guard and meta): required fields present; `slug` matches the folder name and `^[a-z0-9-]+$`; tags obey the dev.to limits; `og_image` exists if set.

### site.yml

```yaml
title: "Grant Petersen-Speelman"
```

## 6. Ruby tooling

Ruby 3.3+. Suggested gems: `commonmarker` (GitHub-flavoured markdown rendering), `nokogiri` (HTML parsing), `webrick` (preview server), `minitest`. Keep dependencies to that unless there is a strong reason.

### 6.1 `bin/meta`: feed and sitemap

Builds `site/feed.xml` (RSS 2.0) and `site/sitemap.xml` from every `site/posts/*/index.md`, sorted newest first. `--check` regenerates into memory and exits non-zero if the committed files differ.

Feed requirements (these come from how dev.to's RSS import behaves, so follow them exactly):

- Include the `content` namespace; each item's full post body goes in `<content:encoded>` as HTML **rendered deterministically from the markdown** (not taken from Claude's page).
- All `src`, `srcset` and `href` values in item content are **absolute** URLs.
- `<link>` and `<guid isPermaLink="true">` are both the canonical URL `https://grant-ps.com/posts/<slug>/`. The guid must never change for a published post (it prevents duplicate imports).
- One `<category>` per tag, at most 4.
- `<pubDate>` from `date` in RFC 822; `<description>` from frontmatter `description`.
- If `og_image` is set, also emit it as an `<enclosure>` with an absolute URL.
- Channel includes `<atom:link rel="self">` to `https://grant-ps.com/feed.xml`.
- Output is byte-stable: running meta twice with no changes produces identical files.

Sitemap: home page plus every post URL, `lastmod` from `updated` or `date`. `site/robots.txt` is static and points at the sitemap.

### 6.2 `bin/guard`: fidelity guard

Proves the generated page contains the author's words exactly. For each post checked:

1. Render `index.md` to HTML with the same renderer as the feed.
2. Parse `index.html` and take the element marked `[data-post-body]`. Remove every descendant marked `[data-flare]`.
3. From both sides, build a sequence of **blocks**: headings, paragraphs, list items, blockquotes, table cells, and code blocks. Extract text; normalise whitespace (collapse runs, trim) but **do not** normalise quotes, dashes or other characters. Code blocks keep their line structure (compare line by line after trimming trailing whitespace), so a dropped line fails even if syntax highlighting wraps tokens in spans.
4. The sequences must match exactly, in order. Additional wrapper elements, classes and attributes in Claude's HTML are fine; missing, added, reordered or altered text is not.
5. Every image `src` and link `href` in the markdown must appear in the post body, resolving to the same target.
6. The page's `<h1>` text equals the frontmatter `title`; the page has `<link rel="canonical" href="https://grant-ps.com/posts/<slug>/">`.

On failure, print the post, the first mismatched block from each side, and a short diff, then exit non-zero. Messages must be clear enough that Claude can fix its own output without a human.

### 6.3 `bin/precommit`

Runs on staged changes and blocks the commit if any of these fail:

- **Slug checks:** frontmatter `slug` equals folder name for every staged post. A post folder that exists in `HEAD` under `site/posts/` must not be deleted or renamed (published slugs are frozen). Allow an explicit escape hatch via an environment variable (`ALLOW_SLUG_CHANGE=1`) and print a warning explaining the consequences (broken canonical URLs and dev.to links).
- `bin/guard` on every staged post (a post counts as staged if any file in its folder is staged).
- `bin/meta --check`.
- Nothing under `drafts/` is staged (belt and braces alongside `.gitignore`).

### 6.4 `bin/preview`

Serves `site/` on `http://localhost:4000` with directory index handling that mirrors production (`/posts/<slug>/` serves `index.html`). Print the URL of the post being previewed when given a slug.

### 6.5 Tests

Minitest, with fixtures under `test/fixtures/`. At minimum:

- Guard passes a known-good page.
- Guard fails on: a dropped paragraph; a reworded sentence; a changed quote character; a dropped code line; reordered list items; a missing link.
- Guard ignores content inside `[data-flare]`.
- Feed: absolute URLs, guid equals canonical URL, max 4 tags, valid XML, byte-stable across runs.
- Frontmatter validation rejects bad slugs and bad tags.

Fixture posts must **never** appear under `site/`, so they never reach the feed or dev.to.

## 7. The publishing skills

These are the heart of the system. Future Claude sessions will know how to publish only what these files tell them, so write them carefully.

### 7.1 `/publish <slug>` (`.claude/skills/publish/SKILL.md`)

Steps the skill must instruct:

1. Confirm `site/posts/<slug>/index.md` exists and its frontmatter validates. If the post is still in `drafts/`, move it (ask Grant first if unsure).
2. Read `design/BRIEF.md` and `design/shell.md`.
3. Write `site/posts/<slug>/index.html` following the shell exactly, with the post body inside `[data-post-body]`. Creative flare goes in clearly marked `[data-flare]` elements and/or `flare.*` files in the post folder.
4. Regenerate `site/index.html` (post list newest first, plus "Writing elsewhere" from `site.yml`).
5. Run `bin/meta`.
6. Run `bin/guard <slug>`. If it fails, fix the HTML and re-run until it passes. Never "fix" the markdown to match the HTML.
7. Run `bin/preview` and give Grant the local URL. Do not commit; Grant reviews, then commits and pushes.

Rules the skill must state:

- **Never alter, add to, reorder or omit the author's prose.** The markdown is the text. Visual treatment is yours; words are not.
- Never change a published slug or its URL.
- Every page uses the shell from `design/shell.md`.
- No em-dashes in any copy you write for the site (page chrome, alt text you add, captions). Use commas, colons or full stops.
- Flare must degrade gracefully: the post must read correctly with flare JS disabled.

### 7.2 Page shell (`design/shell.md`)

Every generated page must include:

- `<link rel="canonical">` to its absolute URL.
- Meta description; Open Graph and Twitter card tags (`og:title`, `og:description`, `og:url`, `og:image` absolute, `og:type=article` for posts); falls back to `default_og_image`.
- `<link rel="alternate" type="application/rss+xml" href="/feed.xml">`.
- Cloudflare Web Analytics beacon script if `analytics_token` is set (omit it otherwise).
- Header: site title linking home, and a "Source" link to `repo_url`.
- On posts: title as the single `<h1>`, publication date, tags, and a "Read the markdown source" link built from `source_url_template`.
- Footer: feed link, repo link.
- Shared CSS from `site/assets/`, with per-post CSS only for flare.
- Semantic, accessible HTML: landmarks, alt text, sufficient contrast, readable at phone width.

### 7.3 `regenerate-site` (`.claude/skills/regenerate-site/SKILL.md`)

For redesigns: update `design/BRIEF.md` (and `shell.md` if needed) with Grant, then regenerate every post page, the home page and 404 page following the `/publish` rules, run `bin/meta` and `bin/guard --all`, and preview. Explicitly: URLs, slugs, feed guids and markdown are untouched by a redesign.
